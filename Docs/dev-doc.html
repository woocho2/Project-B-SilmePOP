3판 규칙 엔진

판의 표현

  • 칸 번호 = y × 17 + x (0 ~ 169). 네트워크와 결과용 스냅샷은 칸 번호로 주고받음.
  • BoardModel은 칸 → BoardSlime 배열. 빈칸은 null.
  • 합체 슬라임은 네 칸이 같은 BoardSlime을 가리킴(Cells 4칸, Anchor는 왼쪽 아래). GetSlimesInCells가 중복을 제거하므로 합에 한 번만 들어감.
  • 판이 바뀌면 이벤트로 알림: SlimesRemoved · SlimeChanged · SlimeMoved(조커) · SlimesMerged. 화면은 이것만 듣고 그림.

조합 찾기 — MatchFinder

17 × 10 판의 사각형은 C(18,2) × C(11,2) = 8,415개뿐이라 전부 봐도 충분히 빠릅니다. 칸마다 2차원 누적합을 만들어 사각형 하나의 합을 배열 조회 네 번으로 구합니다.

  • 합체 슬라임의 숫자는 Anchor 칸에만 넣고, 사각형이 네 칸 중 일부만 걸치면 따로 더함.
  • 한쪽 모서리를 고정하고 넓혀 갈 때 합이 목표를 넘으면 그 방향은 더 보지 않음(숫자가 모두 양수라 합이 줄지 않음).
  • 제공: HasAnyMatch(막힘 판정) · FindFirst · FindAll(AI·돋보기).

터뜨리기 한 번의 순서

순서하는 일
①마우스를 놓는 순간 Physics2D.OverlapBoxAll로 상자 안 칸을 모음 (끄는 동안의 Trigger 결과는 강조 표시에만 씀)
②칸 → BoardModel.GetSlimesInCells (합체 중복 제거)
③숫자 합 = 목표 합인지 확인. 아니면 빨간 상자 흔들림 연출
④ScoreCalculator.Calculate로 점수
⑤BoardModel.Remove → SlimesRemoved → 화면 갱신·터짐 연출
⑥GameManager.AddScore → 마지막 득점 시각 기록 → 서버로 점수 보고
⑦MatchFinder.HasAnyMatch가 false면 "막힘" 안내 (판은 끝내지 않음)

조커는 드래그 중에도 움직이므로, 판정은 항상 ①의 순간의 판을 기준으로 합니다.

점수 — ScoreCalculator

B = 슬라임들의 기본점수 합 (기본 1 · 악마 1 · 천사 2 · 킹 1 · 조커 3 · 합체 = 합쳐진 기본점수 합)
점수 = B + Σ천사(B × 2) + Σ악마(B × −1) + Σ킹(10) + Σ조커(목표 합 × 2)
파괴 아이템 = 그 슬라임의 기본점수만 · 합체 결과가 0 = 합쳐진 수 × 4

규칙 숫자는 모두 GameRules 한 곳에 모으고, 기획서의 예시 점수를 테스트 정답으로 옮겨 고정했습니다.

4시드와 결정성

모든 참가자가 같은 판으로 겨루려면, 판을 서버에서 통째로 보내지 않고 시드 하나만 공유해 각 PC가 똑같이 만들어 내야 합니다. 그래서 무작위가 필요한 곳마다 난수의 출처를 나눴습니다.

무엇난수결과
판 (숫자·특수 배치)GameRandom(seed) — 칸 번호를 섞어 앞에서부터 킹 2 · 천사 3 · 악마 5모두 같음
목표 합GameRandom(seed)의 첫 값으로 10 ~ 15모두 같음
이번 판의 아이템GameRandom(seed × 7919 + 17)로 6종을 섞어 앞에서 1개모두 같음
아이템 효과 (변신·숫자변경·조커·돋보기)아이템마다 GameRandom(seed × 31 + 종류)를 따로 둠같은 순서로 쓰면 같은 결과
조커 이동판 안의 별도 난수참가자마다 다를 수 있음
AI의 반응 시간·실수AI마다 별도 난수판과 무관
자리 번호로 시드를 나누지 않습니다. 같은 판 경쟁에서 시드 차이로 유불리가 생기면 안 되기 때문입니다. 판 생성 난수와 아이템 난수를 다른 시드로 나눠, 한쪽에서 난수를 몇 번 쓰든 다른 쪽 결과가 흔들리지 않게 했습니다.

5아이템 시스템

  • 전략 패턴: SkillBase(대상이 필요한가, 범위 GetArea, 쓸 수 있는가 CanApply, 적용 Apply)를 6종이 각자 채움. 공통 규칙(조커·합체는 대상 아님)은 베이스에 한 번.
  • 사람과 AI가 같은 클래스: SkillSet(참가자 한 명의 아이템과 남은 횟수, TryUse)을 SkillManager(사람)와 AiAgent(AI)가 함께 씀. 규칙을 고치면 둘 다 바뀜.
  • TryUse는 쓸 수 없으면 아무것도 바꾸지 않음(횟수 포함). 대상 고르기를 ESC로 취소하면 횟수를 쓰지 않음.
  • 범위 미리보기는 슬라임 외곽선(가능 초록 · 불가 빨강), 판 밖은 잘라서 표시.

Firebase를 REST로 — FirebaseRestClient

기능방식
인증Identity Toolkit REST로 이메일 회원가입·로그인 → ID 토큰(1시간). 끝나기 전에 Secure Token으로 갱신하고 실시간 수신을 새 토큰으로 다시 연결
읽기 · 쓰기GET / PUT / PATCH / POST / DELETE. PATCH는 "slots/1/kind" 같은 경로 키로 여러 곳을 한 번에
트랜잭션X-Firebase-ETag로 읽고 if-match로 씀. 그사이 누가 바꿨으면(412) 다시 읽어 최대 8번 재시도 — 방 입장, 자리 정리, AI 추가, 계정 번호 발급에 사용
실시간 수신text/event-stream(SSE)을 직접 받아 put / patch 사건 단위로 자름. 글자가 여러 조각에 걸쳐 올 수 있어 한 사건이 다 모인 뒤 UTF-8로 변환. 끊기면 다음 하트비트에서 다시 연결
서버 시각서버 타임스탬프를 써 보고, 돌아온 값과 요청 왕복의 가운데 시각의 차이로 내 시계를 보정. 경기 시간은 모두 이 ServerNow로만 잼

한 판의 동기화

순서하는 일
①방장 StartMatch: seed · targetSum · startAt(지금 + 5초) · 빈 점수표 · state=Playing을 PATCH 한 번으로 씀 → 모두 같은 순간에 시작 정보를 받음
②각자 대기실에서 5초를 센 뒤 게임 씬으로. 도착하면 loaded/s자리를 씀
③방장: 사람이 모두 도착했거나 startAt + 15초가 지나면 playAt = 지금 + 1초를 씀
④모두 playAt(서버 시각)에 맞춰 3, 2, 1 → 180초
⑤점수가 바뀔 때마다 scores/s자리를 PATCH. AI 자리는 방장이 대신 올림
⑥시간 끝: 각자 최종 판을, 방장은 AI 판까지 올리고 state=Result
⑦먼저 대기실로 돌아가는 사람이 state=Waiting으로 되돌리고 점수·최종 판·나감 기록을 지움 (나간 사람의 자리도 비움)

끊김과 방장

  • REST에는 "연결이 끊겼다"는 알림(onDisconnect)이 없으므로 하트비트로 판정: 5초마다 lastSeen을 쓰고, 15초 동안 없으면 끊긴 것으로 봄.
  • 방장이 끊긴 사람을 정리: 대기 중이면 자리를 비우고, 대전 중이면 기권으로 표시.
  • 방장이 끊기면 살아 있는 사람 중 자리 번호가 가장 앞인 사람이 스스로 방장을 맡음.
  • 제대로 나가지 못한 방(대전 중 게임 종료 등)은 다음 접속 때 찾아서 나감.

7AI

클래스역할
AiAgentAI 한 명의 생각(순수 C#). 무엇을 할지 정해 판에 적용하고 다음 행동까지 기다릴 시간을 돌려줌. 시뮬레이션도 이것을 그대로 돌림
AiBrain수 고르기: 목표 합 사각형을 모두 찾고, 정확도만큼은 전략으로 가장 좋은 수, 나머지는 아무 수. 틀린 드래그는 하지 않음
AiSkillAdvisor아이템을 쓸 곳과 가치(점수로 환산). 가치 = 바로 얻는 점수 + 새로 생기는 조합 − 없어지는 슬라임이 앞으로 벌 점수. 결과가 무작위인 아이템도 실제 결과는 보지 않고 가능성만 따짐
AiStrategy전략 기준값. 모든 난이도가 같은 값을 쓰고 정확도·반응 시간만 다름
AiDifficultyTable난이도별 반응 시간, 정확도, 목표 합별 반응 시간 배율
AiPlayerUnity 래퍼. 방장 PC에서 AI 자리마다 하나. 시간을 재고 점수를 서버로 보냄. 시연용 자동 플레이에서는 내 판을 사람처럼 끌어서 둠
AiSimulator화면 없이 한 판을 끝까지 (여러 스레드로 여러 판)

전략을 찾은 방법

  • 지옥 속도·정확도 100%로 504판 탐색 + 새 시드 200판 검증.
  • 가장 큰 차이는 CountWeight = −3: 같은 점수면 슬라임을 적게 쓰는 수(큰 숫자부터)를 고르면 작은 숫자가 남아 판이 늦게 막힘 → 평균 제거 129 → 150마리, 점수 187 → 208점.
  • 한 수 앞 보기는 지금 속도에서 ±1마리 차이라 끔 (0.5 ~ 1초 속도에서만 +2 ~ 5마리).
  • 아이템은 막혔을 때만이 아니라 이득이 기준값(조커 20 · 합체 12 · 파괴 12 · 숫자변경 6점)을 넘으면 씀. 마지막 20초에는 기준을 0.3배로 낮춤(남기면 손해).

방장 PC에서만

AI는 방장 PC에서만 만들어집니다. 다른 PC에서도 만들면 같은 자리 점수가 두 번 올라가기 때문입니다. AI는 화면이 없으므로 BoardModel만 쓰고, SlimeManager는 내 판만 그립니다.

8화면과 연출

  • 슬라임 170칸은 한 번만 생성하고, 슬라임이 없어지면 그림과 콜라이더를 끔. 재대결 때도 다시 만들지 않고 다시 그림.
  • 연출은 DOTween: 터짐(부풀었다 쏙, 0.035초 시간차), 틀린 드래그 흔들림, 순위 슬라임 이동, 패널 전환(PanelTransition), 뽑기 룰렛.
  • ScorePopup은 월드 TextMeshPro 글자를 모아 두었다가 다시 씀(풀).
  • UI는 씬마다 UIManager_씬이 패널을 켜고 끄기만 하고, 각 패널의 일은 패널 스크립트가 맡음(Login_LoginPanel, RoomPanel, Game_RankPanel …). 버튼 연결은 UIButtons.Bind로 코드에서만 — 클릭 소리를 한 곳에서 붙임.
  • 꾸미기: StyleSettings(고른 색·테마)가 값이 바뀌면 이벤트를 쏘고, MySlimeColor(내 색)·ThemeSkin(테마 색·그림)이 붙은 오브젝트가 스스로 다시 칠함 → 씬과 상관없이 동작.
  • 소리: SoundManager가 BGM 채널 1개와 효과음 채널 여러 개를 돌려 쓰고, 볼륨을 저장.

10설계 결정 기록 (Q&A)

개발하면서 고민했던 질문과, 그 답으로 실제 어떻게 구현했는지를 정리했습니다.

구조

처음 버전의 코드를 그대로 키우지 않고 왜 규칙을 따로 뺐나?

처음 버전은 슬라임 오브젝트가 자기 숫자를 UnityEngine.Random으로 직접 뽑고, 합 판정은 물리 Trigger 누적, 점수는 드래그 매니저의 필드였음. 시드 대전이 불가능하고, 화면 없는 AI 판이나 시뮬레이션을 만들 수 없었음.

구현판의 진짜 상태를 순수 C# BoardModel로 옮기고, SlimeManager·SlimeController는 그 이벤트를 듣고 그리기만 함. 내 판·AI 판·시뮬레이션·테스트가 같은 코드를 씀.

상대마다 객체(IOpponent)를 두는 게 자연스럽지 않나?

4인 대전에 AI까지 섞이면 "다른 사람 PC의 사람", "내 PC의 AI", "다른 PC의 AI"가 생겨 경우가 많아짐.

구현상대마다 객체를 두지 않고 모든 점수가 네트워크를 거침. 내 점수는 내가, AI 점수는 방장이 서버에 올리고, 점수판은 서버에서 온 점수만 봄 — 사람이든 AI든 같은 길.

네트워크 요구사항이 정해지지 않았는데 어떻게 먼저 만들까?

어떤 서버 기술을 쓸지 확정되기 전에 게임 흐름부터 만들어야 했음.

구현게임 코드는 INetworkService 인터페이스만 앎. 먼저 LocalNetworkService(메모리)로 로비 → 방 → AI 대전 → 결과를 혼자 끝까지 만들고 테스트한 뒤, 같은 약속을 지키는 FirebaseNetworkService를 끼움. 인스펙터에서 둘을 바꿀 수 있어 혼자 테스트할 때는 계속 Local을 씀.

Firebase Unity SDK를 쓰면 편한데 왜 REST로 직접 했나?

Firebase Unity SDK의 Windows 지원은 베타였음.

구현UnityWebRequest로 인증·CRUD·트랜잭션·SSE 실시간 수신·서버 시각을 직접 구현(FirebaseRestClient). JSON 파서도 작게 직접 둠. 대신 SDK가 해 주던 끊김 알림이 없어 하트비트로 대신함.

판과 입력

드래그 판정을 Trigger로 모은 목록으로 하면 안 되나?

Trigger 결과는 물리 업데이트 주기에 묶여 있어, 빠르게 끌고 바로 놓으면 마지막 범위를 놓칠 수 있음.

구현놓는 순간 Physics2D.OverlapBoxAll로 한 번 더 확인해 판정하고, Trigger 결과는 끄는 동안의 초록·빨강 강조에만 씀.

터진 슬라임은 Destroy하면 되지 않나? 풀은 안 쓰나?

Destroy는 프레임 끝에 일어나 같은 프레임의 계산이 틀어지고, 재시작마다 170개를 새로 만들었음.

구현칸 170개를 한 번만 만들고 슬라임이 없으면 그림과 콜라이더만 끔. 칸 수가 고정이라 따로 오브젝트 풀은 두지 않음. 자주 생기고 사라지는 "+점수" 글자만 풀로 씀.

자리마다 시드를 다르게 하면 더 자연스럽지 않나?

같은 판 경쟁에서 시드 차이로 유불리가 생기면 안 됨.

구현모든 참가자가 같은 경기 시드. 대신 판 생성·아이템 선정·아이템별 효과의 난수를 서로 다른 시드로 나눠, 한쪽에서 난수를 쓰는 횟수가 다른 쪽 결과를 흔들지 않게 함(4장).

네트워크

PC마다 시계가 다른데 어떻게 동시에 시작하나?

각 PC의 시계로 카운트다운을 하면 몇 초씩 어긋남.

구현접속할 때 서버 타임스탬프를 써 보고, 요청 왕복의 가운데 시각과 비교해 내 시계와의 차이를 구함. 시작 시각(startAt, playAt)은 서버 시각으로 정하고 모두 ServerNow로만 잼.

씬을 불러오는 속도가 PC마다 다른데, 늦은 사람은 어떻게 하나?

시작 시각만 정해 두면 늦게 불러온 사람은 이미 몇 초 늦은 판을 시작함.

구현각자 게임 씬에 도착하면 loaded를 쓰고, 방장이 모두 도착했거나 15초가 지나면 그때 playAt(지금 + 1초)을 정함. 모두 그 시각에 3, 2, 1을 시작.

두 사람이 동시에 같은 자리에 들어오면?

읽고 → 고치고 → 쓰는 사이에 다른 사람이 바꾸면 한쪽이 덮어씀.

구현ETag 조건부 쓰기 트랜잭션: 읽은 뒤 그사이 바뀌었으면(412) 다시 읽어 재시도. 방 입장·나감, AI 추가(그사이 사람이 들어왔으면 넣지 않음), 계정 번호 발급(동시에 가입해도 번호가 겹치지 않음)에 씀.

시작할 때 여러 값을 따로 쓰면 받는 쪽이 반쯤 바뀐 방을 보지 않나?

seed, targetSum, startAt, state를 따로 쓰면 그 사이에 이벤트가 도착할 수 있음.

구현시작 정보 전부와 빈 점수표를 PATCH 한 번으로 씀 → 모두가 같은 순간에 완성된 시작 정보를 받음.

게임 디자인을 코드로

AI 난이도를 점수로 비교하면 안 되나?

점수는 천사·킹·악마를 어떻게 만났는지에 따라 크게 흔들림.

구현난이도 비교는 슬라임 제거 수로. 사람의 기록을 CSV로 남기고 같은 시드로 AI에게 다시 풀게 해, 목표 합별 반응 시간 배율을 구함(기획서 11장).

돋보기가 최선의 수를 알려 주면 안 되나? 조커는 원하는 곳에 두면 안 되나?

돋보기가 최선의 수를 알려 주면 일찍 써서 킹 조합을 찾는 것이 정답이 되고, 조커를 원하는 곳에 두면 천사 옆에 넣고 바로 터뜨리는 쉬운 고득점이 됨.

구현돋보기는 악마 없는 조합 중 무작위 하나, 조커는 경기 시드로 칸을 뽑아 가장 가까운 기본 슬라임. 둘 다 누르는 즉시 쓰고, 같은 순서로 쓰면 모든 참가자에게 같은 결과.

난이도마다 다른 AI 로직을 짜야 하나?

난이도마다 로직이 다르면 고칠 곳이 네 배가 되고, 난이도 차이가 "생각의 질"인지 "속도"인지 섞임.

구현모두 같은 전략(AiStrategy.Best)을 쓰고 정확도와 반응 시간만 다르게. 수치는 AiDifficultyTable 한 곳에서만 고침.
